# Инфраструктура первого запуска

**Meshroom работает на временной GPU-ноде Vast.ai.** Постоянная машина управляет заданием и хранит исходники/результаты. Отдельный VPS «для Meshroom» не обязателен.

Это схема предстоящей работы. Аккаунт с балансом, доступ к конкретной машине, runtime и передача файлов пока не подтверждены запуском.

## Где что размещается

| Место | Содержимое и роль |
|---|---|
| Существующий компьютер или VPS владельца | Агент, рецепты запуска, оригиналы/рабочие копии данных и сохранённые результаты |
| Временный GPU-инстанс Vast.ai | Meshroom/AliceVision, копия входных кадров или видео, временный кэш и результаты расчёта |
| Локальная рабочая машина | Просмотр, CloudCompare и build123d на первом этапе, если окружение доступно |
| Этот Git-репозиторий | Контекст, будущие рецепты и конфигурации без секретов, небольшие обезличенные параметры и отчёты |

Конкретный координатор выбираем после проверки диска, доступа и канала. Если существующему VPS мало места, он может только управлять, а данные передаются между компьютером и GPU напрямую. Не публикуем частные hostname и параметры входа.

## Как появляется runtime

Vast.ai штатно использует образ и шаблон, задающий запуск окружения. Для пилота предлагаем один совместимый базовый Docker-образ и воспроизводимый установочный рецепт выбранной версии Meshroom/AliceVision. Собственный образ можно сделать после успешного прогона, если повторная установка мешает. Готовность такого рецепта сейчас не заявлена. [S10](sources.md)

Фиксируем версии/образ и проверяем GPU изнутри контейнера. Не нужно поднимать Docker-in-Docker ради запуска Meshroom. У SSH/Jupyter-шаблонов Vast есть собственная обработка entrypoint; нужную инициализацию надо согласовать с `onstart`, а не предполагать, что любой чужой образ заработает неизменным. [S10](sources.md)

Стартовый ориентир из обсуждения — одна RTX 3090/4090, 32–64 ГБ выделенной RAM и SSD с запасом под кэш. Это **не результат бенчмарка и не универсальный минимум**. Подбираем ресурсы под реальное число и разрешение кадров; смотрим выделенную инстансу RAM/CPU, а не только память всего хоста. GPU и драйвер должны быть совместимы с выбранной сборкой. [S02, S10](sources.md)

Для первого запуска предлагалась аренда on-demand. Она не устраняет обычные сбои хоста; исходники и важные результаты всё равно должны иметь постоянную копию.

## Передача данных

Используем штатные SSH/SCP/SFTP/rsync или `vastai copy`. API автоматизации можно подключить по необходимости; собственный облачный сервис не нужен. Прямой SSH предпочтителен для крупных передач, когда доступен: проксируемый канал может быть медленным. [S11–S12](sources.md)

Временную рабочую папку задания удобно разделить на `input`, `config`, `work` и `output`. Это структура файлов, а не требование разработать хранилище или новый формат. Большие папки располагаются вне репозитория; по умолчанию Git их не получает.

## Жизненный цикл задания

1. До аренды подготовить входные материалы, рецепт, конечный каталог выгрузки и предел стоимости/времени.
2. Создать один согласованный инстанс; записать фактические ресурсы и ставку во внутреннюю карточку задания.
3. Проверить окружение и загрузить данные.
4. Выполнить весь фотограмметрический граф на этой машине; не распределять узлы по разным сервисам без необходимости.
5. Выгрузить облако, камеры, проект/настройки, логи и нужный для продолжения кэш. Сверить наличие и целостность файлов.
6. Удалить временный инстанс, если продолжение не нужно, и убедиться в его состоянии через штатный интерфейс провайдера.

Если передача результатов не удалась, удалять единственную копию нельзя. Остановку можно использовать осознанно для паузы, фиксируя оставшиеся расходы и способ выгрузки.

| Действие Vast.ai | Последствие |
|---|---|
| `stop` | Данные инстанса остаются, начисления за диск продолжаются; GPU для последующего старта не резервируется |
| `destroy` | Инстанс и его локальные данные удаляются; нужные файлы должны быть сохранены заранее |

Такое различие документировано провайдером. Отдельные постоянные тома/внешние хранилища, если позднее будут подключены, имеют собственный жизненный цикл и оплату. [S11](sources.md)

## Стоимость и доступ

Старые ценовые таблицы RunPod/Vast/Selectel/китайских площадок из чата не используются как смета. Перед запуском смотрим реальное предложение, плату за диск и передачу, доступность и условия аренды. Считаем стоимость законченного задания, включая подготовку и повторы.

Создание платных ресурсов требует действующего разрешения владельца и понятного предела расходов. Документирование проекта не является таким запуском. Если разрешение уже выдано в пределах задания, не нужно повторно спрашивать о каждом техническом шаге.

API-токен и SSH-ключи хранятся в среде исполнения агента/штатном хранилище учётных данных. Они не попадают в Git, логи и переписку. Используем доступ, необходимый для выбранных операций. [S12](sources.md)

## Что сохранять в Git и вне него

**В Git:** инструкции, будущий установочный рецепт, проверенные команды, конфигурации с placeholders, исходник модели без частных данных, при необходимости небольшие обезличенные параметры и отчёт.

**Вне Git:** видео/фото, большие облака и сетки, весь Meshroom cache, приватные координаты и снимки объекта, учётные данные, полные журналы с адресами доступа. Удобный preview можно добавить отдельно после проверки содержимого; `.gitignore` не заменяет осмотр diff.

Повторный запуск зависит от сохранённых исходников, версии графа, настроек и масштаба. Кэш полезен для продолжения, но его объём и необходимость выгрузки выбираются осознанно. Сохранение кэша само по себе не гарантирует переносимость между версиями.

## Что сейчас не требуется

Отдельный VPS, постоянная GPU, собственный registry, S3, Kubernetes, несколько провайдеров, новый MCP-сервер и отдельный планировщик не входят в начальную схему. Они могут появиться только под реальную потребность после одного сквозного результата.
